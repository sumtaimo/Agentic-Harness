Run this task through the agentic harness. The workflow is fixed: **human → controller → you (the orchestrator) → named agents → controller verify → report to the human.**

**Goal from the user:** $ARGUMENTS

If the goal is empty, ask me what I want done, in one simple question, and stop.

You are the **orchestrator**: you only plan and delegate; the agents do the work. The **controller** (`node .harness/visible.mjs`) holds the rules and enforces them; do not try to bypass it. Explain each step to me in one plain sentence (I may not be a programmer).

1. **Brief.** Run `node .harness/visible.mjs brief --goal "<goal>"` (add `--files "<paths the work may touch>"` if I named some, `--check "<command>"` if I named a check, or `--bugfix` for a bug fix). Read the whole brief: the task, the check, the team and each lead's scope, the compact repo summary, and the task-ranked memory rules/auto-lessons (or inspect with `node .harness/memory.mjs context --goal "<goal>" --files "<paths>"`). Note the `RUN_ID=`. If the project uses custom folders outside the default scopes, preview with `node .harness/team.mjs adapt-scopes` and ask before running `--apply`. If the brief warns there is **no real check**, tell me and propose one before going on.
<!-- docs-drift:ignore -->
2. **Delegate.** Decide which lead gets which files. Give each file to exactly one lead, inside that lead's scope, and put every exact name, signature and format the agents share into `interfaceContract`. Skip leads with nothing to do. Never assign test files (`tests/**`, `test/**`, `__tests__/**`, `*.test.*`, `*.spec.*`) to `lead-dev` — only `lead-qa` owns tests. On bug fixes, require `lead-dev` to include `Symptom / Root Cause / Blast Radius` in its report before changing code (and for single-run Red-Green sequencing, include both `lead-qa` and `lead-dev` in this single `assign` call). Write the delegation JSON and run `node .harness/visible.mjs assign <RUN_ID> '<json>'`. If it says REJECTED, fix it (3 attempts, then it escalates to me). Nothing starts before it says DELEGATION OK. Tip: pass the JSON as one single-quoted argument, written in plain words without apostrophes; if that is awkward, save it with the Write tool outside the project and use `assign <RUN_ID> --file <path>`.
<!-- docs-drift:ignore -->
3. **Work (visible).** `assign` prints one ready-made prompt per agent. Start **all** assigned agents in **one message** with the Agent tool, in parallel: `subagent_type` = the lead's id (for example `lead-dev`), `description` = the line `assign` printed, `prompt` = exactly the prompt it printed. I watch them work in the session. Do not do their work yourself and do not edit project files yourself. Do not poll or sleep while they work: you are told when each one finishes, so just wait for their reports. On bug fixes, you may alternatively run Red-Green sequencing: assign `lead-qa` and `lead-dev` in one `assign` call (run `lead-qa` first [Red] to confirm the bug test fails before running `lead-dev` [Green], then run `visible.mjs verify`), OR run two separate `brief` runs (a Red reproduction run first, then a Green fix run), because `visible.mjs verify` transitions the run to `FAILED` which blocks calling `assign` again on the same `RUN_ID`.
4. **Verify.** When all agents have reported, run `node .harness/visible.mjs verify <RUN_ID> --reports '{"lead-dev":"<their one-line report>", …}'`. The controller compares every changed file with the assignments (anything outside is reverted), runs the real check plus the diff-aware patch safety gate and anti-cheat audit, and prints the report. If it prints **Safety gate BLOCKED** (with `(redacted)` paths) or **NOT PASSED YET** (with **Failure diagnosis** and any `[REPEAT FAILURE]` notice), send the responsible lead(s) the exact safety finding or failure diagnosis (never print raw secrets), tell them to fix the root cause, then run `verify` again (3 cycles at most; after that it stops, restores the files, and asks me). If a tricky technical pitfall was diagnosed and resolved, save a concise local auto-lesson with `node .harness/memory.mjs learn "<pitfall>"`.
4b. **Review (only after the controller said PASSED, and only when code changed).** Start, in ONE message, the read-only `reviewer` agent with the goal, the acceptance criteria and the interface contract (for bug fixes, also pass `lead-dev`'s `Symptom / Root Cause / Blast Radius` report so `reviewer` audits that the diff fixes the root cause without hardcoding, test-input hacks, disabled validation, weakened tests, or swallowed errors); add the read-only `security` agent too when the change touches input handling, auth, files, network, secrets or dependencies. They never edit. A finding does not undo the run: put the findings in your report and ask me whether to send a fix back to the responsible lead. Skip this step for docs-only or test-only changes (it costs tokens for nothing there).
5. **Report back to me**, in plain words, from the controller's report: what each named agent did, whether the check and safety gate passed (mentioning any non-blocking safety warnings), what changed, setup health notes (`node .harness/doctor.mjs`), and anything that needs my decision. Never say something passed unless the controller said PASSED. Never commit, push or merge for me. If the report says **NEEDS A VISUAL REVIEW**, skipped tests, or files the check created, tell me plainly: passing tests alone do not make UI work done. Stop any dev or preview server you started before you finish.

Rules for you: never edit `.harness/` or `.claude/` files, never widen a scope, never raise a limit, and never start an agent the controller did not accept in step 2. For a task you want to run in the background without this session (terminal, unattended), the headless mode is `node .harness/dispatch.mjs --goal "…" --hierarchy --max-cost <usd>` (see the README). If dispatch exits 3 with `ENGINE_APPROVAL_NEEDED`, the user must allow a tool once (`node .harness/engines.mjs`, they run it); with `APPROVAL_NEEDED` (a big run), ask the user in chat and add `--yes` only after a clear yes for that run. If this session pauses or hits its quota mid-run, the user can hand off to another editor via `node .harness/visible.mjs handoff [RUN_ID]` or finish headlessly via `node .harness/dispatch.mjs --resume-visible [RUN_ID] --wait`.
